Overview

This explorer covers the Dogecoin main chain: blocks, transactions, addresses, the pending set, fees, mining, and the protocols carried on top of it (Doginals, DRC-20, TAP on Doge, Dunes).

This explorer covers the Zcash main chain: blocks, transactions, transparent addresses, the pending set, fees, mining, and the protocols carried on top of it (Zerdinals, ZRunes, ZRC-20). Shielded activity is covered only to the extent the chain makes it public; see the Privacy section.

Every reading is first party: it comes from our own {{ profile.name }} node and our own indexers. Nothing is fetched from a third-party explorer, and no number appears without a source that proved it.

Absent and zero are different answers, and the pages keep them apart. A fee the node did not report reads as "not derived", not as 0. A miner without attribution evidence reads as Unknown, never as a guessed pool name.

Block timeline

The timeline is a strip of cubes. To one side are confirmed blocks, newest first, each carrying its exact height, age, transaction count, size, fees where derived, and the attributed miner. To the other side are future target slots.

A future slot's height is derived arithmetic: the freshest tip this page holds, plus one for each slot outward. Those heights are expectations about numbering, not claims about content.

The minutes shown against future slots come from the chain's target spacing. A target is an expectation, not an arrival time, which is why no countdown is shown anywhere.

When a block confirms, it joins the confirmed side and the future slots renumber from the new tip. On a reorganisation, blocks from the replaced branch drop off the strip and the same heights refill from the branch that won.

Candidate blocks

The future side of the timeline shows candidate buckets, which are a weaker and more honest claim than projected blocks. A projected block says "this is what the next block will contain". A candidate bucket says only "this is what is waiting, grouped under the chain's own fee rules".

The capability document publishes projectedBlocks: false for this chain, and the buckets carry that honesty forward: no ETA is derived, and no bucket is presented as the next block.

Dogecoin: an ordering under the relay policy

Dogecoin buckets are ordered by the fee policy nodes relay by, measured in koinu per kilobyte, and packed against the consensus block size limit. Miners commonly build against a smaller soft cap this explorer does not claim to know, so the ordering is a reading of the pending set, not a forecast of the next mined block.

A projection audit runs continuously, comparing this ordering with the blocks actually mined. Until that audit proves the ordering predicts block content, projectedBlocks stays false. Transactions whose fee cannot be read are placed in no bucket at all: not knowing a fee must neither promote nor demote a transaction.

Zcash: ZIP-317 eligibility tiers

Zcash block producers select transactions by weighted random sampling under ZIP-317, so no ordering of the pending set is honest. Instead of an order, the buckets are eligibility tiers: pays its conventional fee, pays less than convention, fee not readable, and expiring.

A shielded transaction's fee cannot be read from its transparent side, so it sits in the fee-not-readable tier, never assumed paid or unpaid. An expiring transaction may leave the pending set without ever confirming. Whether an underpaying transaction gets in depends on each producer's unpaid budget, which this explorer does not model. No promised order exists between or within tiers, and none is shown.

Fees

Dogecoin fees are quoted in koinu per kilobyte, the chain's own unit. This explorer never quotes sat/vB here: that is a Bitcoin unit and it has no meaning on this chain.

The fee panel shows four levels (no, low, medium, high priority), and each figure names its basis. The first choice is the node's own estimatesmartfee estimator. When the estimator cannot answer, levels fall back to quantiles of the current pending set, then to recent confirmed blocks, and finally to the relay floor.

When the pending set is sparse there is little evidence to price against, and the levels sit at or near the relay floor. That is the honest answer: on a chain with empty blocks, the floor is what it costs.

Zcash fees follow ZIP-317: a transaction pays for its logical actions, not its byte size, so a rate per byte would be the wrong number. This explorer never quotes sat/vB or any per-byte rate here.

The conventional fee is 5,000 zatoshi of marginal fee per logical action, with a grace allowance of 2 actions. A typical transparent spend counts 2 actions, so its conventional fee is 10,000 zatoshi. The panel also shows what share of the current pending set pays at least its conventional fee, when the pending set can be read.

Pending transactions

The pending set is our own node's mempool: the transactions it has accepted and would relay, read directly from it. No pending transaction is imported from anywhere else, so this is one node's view, stated as such.

Lifecycle

A transaction the explorer has seen carries one of these states: seen in the pending set, waiting for a block, confirmed in a block, replaced by another transaction, in conflict with a confirmed transaction, dropped from the pending set, expired before confirming, removed by a chain reorganisation, or removed for a reason the node did not state. That last state is real: when the node drops a transaction without saying why, the page says exactly that.

Zcash transactions carry an expiry height. Past it, a transaction leaves the pending set without a block, and its page says it expired rather than leaving it forever "pending".

When a pending transaction is replaced by another spending the same inputs, the replaced one keeps its page and names its replacement, so a payment that "disappeared" can be followed to where it went.

Difficulty

The target spacing is 75 seconds per block, set by the Blossom upgrade. The observed figure is the mean interval over the recent collected window.
Subsidy
A fixed 10,000 DOGE per block since block 600,000. There is no halving schedule; supply grows by roughly 5 billion DOGE per year.
The subsidy halves on a schedule. Part of each subsidy is directed by consensus to development funds and, since NU6, to a lockbox; the subsidy shown on these pages is the miner's share as the node reports it.

Merged mining (AuxPoW)

Since block 371,337 Dogecoin allows merged mining through AuxPoW: a Litecoin miner embeds a commitment to a Dogecoin block in its Litecoin work, so one round of scrypt hashing can win both chains. Most Dogecoin blocks are found this way, which is why the pool table is dominated by Litecoin pools.

Pool attribution

A block is attributed to a pool only on evidence, checked in this order: a known tag in the coinbase, then a known payout address, then a known tag in the AuxPoW parent chain's coinbase. Within each class, the first matching rule in the dataset wins, and the block's row names the exact evidence that matched.

The rules live in a versioned attribution dataset, and the page prints the dataset version under the table, so a disputed attribution can be traced to the exact ruleset that produced it.

Unknown is a real bucket. A block with no matching evidence stays Unknown; it is never guessed away by similarity, timing, or anything else.

Attribution reads the transparent coinbase only. A shielded coinbase output carries no attribution evidence, so more Zcash blocks stay Unknown than on transparent chains, and that is the honest count.

Privacy

Zcash carries shielded pools (Sprout, Sapling, Orchard) whose senders, receivers, and amounts are hidden by the protocol itself. That is not a gap in this explorer; it is the design of the chain.

What is public, and shown: a transaction's structure, its counts of shielded components (spends, outputs, actions), its transparent inputs and outputs with their values, and the value balance the consensus rules reveal where they reveal it.

What is never shown: the senders, receivers, and amounts of shielded parts. They are unknowable to this explorer, and unknowable is how they are presented. A hidden value is never rendered as zero, because zero is a claim and hidden is not.

Freshness

Every reading carries the height of the source it came from and the timestamp at which it was observed. Relative times like "3 minutes ago" keep the exact timestamp in their tooltip, so the fact behind the phrasing is never lost.

A source that answers from behind the tip is labeled as behind, with the exact block count. A reading whose source stopped answering is labeled unavailable rather than being served from cache as if it were current.

When a source is down, the widget that needs it degrades and says what it is missing. A page never disappears because a source is down: the rest of its readings stay up with their own evidence.

API

Every reading on these pages comes from the HTTP API below, under /api/v1/{{ chain }}/. All endpoints are GET, answer JSON, and take a network query parameter that currently must be mainnet. Numeric quantities cross the API as exact decimal strings, so amounts survive beyond JavaScript number range. All hashes and heights in the examples below are samples, not live data.

Search

Resolves a query (a height, hash, transaction id, transparent address, or protocol asset) to the pages that can answer it. The query must be 1 to 256 printable characters. 

GET /api/v1/zcash/search?q=3050000&network=mainnet

Errors

  • 400: the reference is invalid; the body says which rule it broke, for example "txid must be 64 lowercase hex characters".
  • 404: the reference is valid but the object does not exist on this chain.
  • 503: the source that would answer is unavailable; the body names the source. Any network other than mainnet also answers 503, because only mainnet is served today.

Reorganisations

On a reorganisation, rows for replaced blocks are rolled back and the same heights are refilled from the branch that won. A height you fetched can therefore answer with a different hash later; anchor on hashes when you need a stable reference.
